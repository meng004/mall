## 教师定位工具的复演步骤

1. 逻辑视图看三条依赖：订单控制器到订单服务、订单服务到 `OmsOrderExample`、后台控制器到管理员服务。生成查询对象在“生成代码”边界里。
2. 进程视图只看 `POST /order/cancelOrder`。调用方拿到成功时，订单仍是待付款。真正进入 `cancelOrder` 的是 TTL 到期之后。时序图把接收者收成一条虚线；代码里的调用者是 `CancelOrderReceiver.java:22-23`。
3. 逻辑泄漏一：`OmsPortalOrderController.java:64-69` 的方法名叫取消，方法体只调用 `sendDelayMessageCancelOrder`。用户立刻取消走的是同文件 `:92-96` 的 `/cancelUserOrder`。
4. 逻辑泄漏二：`UmsAdminController.java:148-156` 把服务返回的 `-1`、`-2`、`-3` 译成中文失败文案。整数含义定义在 `UmsAdminServiceImpl.java:246-261`。
5. 依赖生成代码：`OmsPortalOrderServiceImpl.java:367` 在 `list` 里直接 `new OmsOrderExample()`。同一文件 `:307` 和 `:440` 也是这个查询对象。类定义在 `OmsOrderExample.java:8`。
6. 开发视图确认 `mall-admin` 与 `mall-portal` 互不依赖。控制器调用本模块服务再访问数据，不是分层违规。
7. 运行核对：

```bash
rtk proxy mvn -f mall/pom.xml -pl SDC/E2 -am test
```


## 当前 Java 入口

测试命令从包含 `mall` 的工作区运行；若已经在 `mall`，去掉 `-f mall/pom.xml`。首次构建允许 Maven 下载依赖，缓存齐备后可加 `-o`。

IDEA 打开 `SDC/E2/src/test/java` 下的 `LayerRulesTest` 运行 JUnit；打开 `src/main/java/com/macro/mall/sdc/e2/LayerRules.java` 运行 `main`，在解析/定位方法设断点。演示会读取当前仓库并输出结果；JUnit 使用临时受控文件验证行为。

`main` 从工作目录向上查找含 `pom.xml` 与 `mall-portal` 的 mall 根目录，也支持工作区下的 `mall`。IDEA 工作目录可选 mall 或实验目录；任意目录启动时在 VM options 设置 `-Dmall.root=/你的路径/mall`（也接受 E 模块目录）。E2/E5 通过 Maven 依赖复用 E1 工具，IDEA 自动加入 classpath。

这些工具只做只读源码辅助检查，不是 Java/SQL 语义分析器：源码匹配依赖字面格式，注释和改名可能影响结果，需人工复核；不能用静态结果证明数据库事务、支付或消息行为。POM 只读项目直接声明依赖，不计算 profile、依赖管理或传递依赖。旧分析中的行号是历史快照。

## 评审记录

对照源码审过操作说明。三处和“只点一个方法”的讲法不同，以仓库为准：

- 实验点名的是 `list` 使用 `OmsOrderExample`。同一服务在取消订单 `:299` 和另一处查询 `:432` 也直接构造这个生成对象。
- `UmsAdminServiceImpl.java:248` 在改密时同样使用生成的 `UmsAdminExample`。点名的缺陷仍是控制器翻译返回码；生成查询依赖比这一处更广。
- 时序图没有单独画出 `CancelOrderReceiver`。到期后调用 `cancelOrder` 的是这个接收者，不是队列自己。
