## ① 现状

原提交没有库存预警，`PmsSkuStock.java:21` 已有 `lowStock`。当前工作区已包含 E6 的 `warnSku` 和 `getLowStock`；以下区分既有库存链路与新增预警调用，方法名是稳定定位依据，行号会随修改移动。库存被改写的链路：

- 下单 `generateOrder:169` 调用 `lockStock`，随后 `:171` 对每个 SKU 调用 `warnSku`。`warnSku` 在 `:783`。锁定增加在 `:745`。
- 支付 `paySuccess:258` 在 `:268` 调用 `updateSkuStock`，`:270` 调用 `warnSku`，`:272` 仍 `return count`。SQL 在 `PortalOrderDao.xml:55` 只减 `stock` 和 `lock_stock`。
- 超时取消 `:291`、用户取消 `:322` 调用 `releaseSkuStockLock`（XML `:77`）。这里不调用 `warnSku`。
- `hasStock:753` 只拦截可售不足。`lowStock` 的比较在 `warnSku`，不在 SQL 里。

商品表 `PmsProduct.lowStock` 不在这四条链上。下单扣的是 SKU。

## ② 变更计划

已经改的是这两处调用：`lockStock` 返回之后（`:171`）和 `updateSkuStock` 返回之后（`:270`），都进入 `warnSku`。预警不改变 `paySuccess` 的返回值。

不能改：`mall-mbg` 的生成 Mapper；`PortalOrderDao.xml:50-67` 的扣库存算术；`paySuccess:253-264` 的订单状态更新。这些一改，已有支付和取消的调用方就要跟着改。

排除的方案：在 `updateSkuStock` 的 SQL 里做预警。SQL 减的是库存，发不出通知，而且这条语句是支付契约。另一条也不做：低于阈值就拒绝下单。`hasStock` 已经负责“不够卖”，预警不应改变下单结果。

回归范围按调用链，不按改动行数：`generateOrder`、`paySuccess`、`cancelOrder`、`cancelTimeOutOrder`；并核对后台补货与退货分支，不能因不实施就略去影响分析。

退货链：后台 `OmsOrderReturnApplyController.updateStatus` → `OmsOrderReturnApplyServiceImpl.updateStatus`（41–71）→ `OmsOrderReturnApplyMapper.updateByPrimaryKeySelective`。当前代码的“完成退货”只写退货申请状态、收货人、时间和备注，没有更新 `pms_sku_stock`，所以不能声称退货会自动增加库存；这是既有系统限制。本次不补造入库业务，回归需保证退货状态处理不受影响。以后若增加入库，须在真正写库存的服务处重新评价预警触发条件。

后台 SKU 编辑：`PmsSkuStockServiceImpl.update` 过滤 productId 后调用 `PmsSkuStockDao.replaceList`，也会改变库存和阈值。E6 本轮规格限定交易导致可售库存下降时预警，后台补货/阈值编辑不自动发告警；接受“后台单独调低库存不会即时通知”的限制。商品聚合库存与 SKU 库存不是同一字段，不能混算。

改动文件清单：业务只改 `mall-portal/src/main/java/com/macro/mall/portal/service/impl/OmsPortalOrderServiceImpl.java`；行为验证迁入 `SDC/E6/src/test/java`（原测试为 `mall-portal/src/test/java/com/macro/mall/portal/ExperimentOrderTest.java`）；规格、结果分别记入 E6 操作说明和说明。生成模型、Mapper、库存 SQL、退货代码保持不变。

最可能错的是只用 `stock`、不减 `lockStock`。未支付订单已经锁住的数量会看起来仍可售。验证方式是实际 Java 行为测试：`stock 10`、`lock 6`、`low 5` 必须预警；等于阈值和缺阈值不预警；预警查询失败不能改变支付返回值。外部持久化在单元测试里替换，不能据此声称验证了数据库事务或并发。
