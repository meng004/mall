# E5-01 分类删除限制：影响分析

分支 `exp/e5-01`，基线 `baseline-dcaa93b3`。本示例只做影响分析并锁定现状，不改产品代码，不实现拒绝规则。对照结果见 [evidence/compare.txt](evidence/compare.txt)。

## 需求与边界

分类不存在时返回 0。存在直接子分类，或任意商品的 `product_category_id` 指向它（含 `delete_status = 1` 的逻辑删除商品）时拒绝，且不删除。空分类、以及只有其他分类被引用时，仍按主键删除。

不级联删除子分类或商品；不检查筛选属性关系；不解决并发插入；不改生成代码和搜索。

## 现状与调用链

```
POST /productCategory/delete/{id}
  PmsProductCategoryController.delete            controller/PmsProductCategoryController.java:74-82
    PmsProductCategoryServiceImpl.delete         service/impl/PmsProductCategoryServiceImpl.java:105-107
      productCategoryMapper.deleteByPrimaryKey   （仅此一步）
```

- 控制器 `count > 0` 返回成功，否则 `CommonResult.failed()`。服务抛出的 `ApiException` 由 `mall-common` 的 `GlobalExceptionHandler`（23-28 行）转成失败结果。
- 本仓库 `delete` 的调用方只有上述控制器。
- 相邻能力已存在但删除没有使用：`getList`（96-101 行）按 `parentId` 查下级；`update`（70-80 行）按 `productCategoryId` 同步商品里的分类名。
- 存储：`pms_product_category.parent_id`（`document/sql/mall.sql:1430`），`pms_product.delete_status`（1094 行）。生成条件 `PmsProductCategoryExample.andParentIdEqualTo`（177 行）、`PmsProductExample.andProductCategoryIdEqualTo`（239 行）、`andDeleteStatusEqualTo`（629 行）均已存在。

## 锁定现状的测试

[SDCE501Test](../../../../mall-admin/src/test/java/com/macro/mall/sdc/SDCE501Test.java) 调用真实 `delete(101)`，只 mock 分类与商品 Mapper：30 行确认 `deleteByPrimaryKey(101L)`；31-34 行确认没有按主键读取、没有 `countByExample`、没有删除商品。运行前预测与观察一致。这只说明当前仅按主键删除，不是新规则已通过。

| 文件 | 改／不改 | 理由 |

| `PmsProductCategoryServiceImpl.delete` | 改 | 唯一落点。顺序：`selectByPrimaryKey` 为空返回 0；子分类 `countByExample(parent_id = id) > 0` 则 `Asserts.fail`；商品 `countByExample(product_category_id = id)`，不加 `delete_status` 条件，`> 0` 则拒绝；否则 `deleteByPrimaryKey` |
| `PmsProductCategoryController` | 不改 | 0 仍走现有失败返回，拒绝走已有 `ApiException` |
| `mall-mbg` | 不改 | 现成 count 与条件方法够用 |
| `mall-search` | 不改 | 删除不调用搜索；有商品时直接拒绝，空分类没有要同步的商品文档 |
| 表结构 | 不改 | 不加外键 |

## 回归范围

| 输入 | 期望 | 状态 |
|---|---|---|
| 分类 101 现在的 delete | 只按主键删除 | 已由 SDCE501Test 锁定 |
| 不存在 | 返回 0，不调用 `deleteByPrimaryKey` | 计划 |
| 有直接子分类 | `ApiException`，不删除 | 计划 |
| 有未删除商品引用 | 同上，条件只有 `product_category_id` | 计划 |
| 只有逻辑删除商品引用 | 同样拒绝，不能加 `delete_status = 0` | 计划 |
| 空分类，或只有其他分类有商品 | 主键删除成功，不删子分类和商品 | 计划 |

另需回归 `getList`、`update` 的分类名同步不受影响（本题不改它们）。

## 被排除的方案

- 级联删除子分类与商品：需求是拒绝，不是清理；会把引用完整性做成数据清理任务。
- 加数据库外键：要改表并处理现有数据，且外键违例只能得到 SQL 异常，不是项目的失败响应。
- 检查筛选属性关系表：不在两条规则内；删除空分类时关系残留仍可能存在，本次不扩展。
- 只在控制器检查：服务才是删除的唯一业务入口。

## 风险

1. 检查顺序：先确认存在，再查子分类和商品，最后才删除；顺序错了会把"不存在"报成拒绝或误删。
2. 漏掉逻辑删除商品：若沿用列表查询的 `delete_status = 0` 习惯，会放行仍被引用的分类。
3. 并发：检查与删除之间可插入新子分类或商品。`delete` 没有事务和锁，补事务而不锁行也挡不住，不宣称并发完整性。
