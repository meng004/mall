# E5-00 库存预警影响分析

分支 `exp/e5-00`，基线 `baseline-dcaa93b3`。本示例只做影响分析并锁定现状，不改产品代码，不实现预警。对照结果见 [evidence/compare.txt](evidence/compare.txt)。需求与 `origin/exp/e6-00`、Issue #26 相同：SKU 可售库存严格低于该 SKU 的 `lowStock` 时告警；等于、阈值为 null 不告警；预警只读，不改库存；读取预警数据失败不得改变已成功交易的返回值。预警查询抛 `DataAccessException` 时记「预警不可用」日志并返回，日志只含 SKU、数量、阈值。

## 需求与边界

可售库存 = `stock - lockStock`。基线已按这个式子计算可售：`OmsPromotionServiceImpl.java:53` 为 `setRealStock(skuStock.getStock() - skuStock.getLockStock())`，同式还在 73、96、167 行。严格小于 `lowStock` 才记预警日志；等于阈值、SKU 不存在、`lowStock` / `stock` / `lockStock` 任一为空，都不告警。预警只读，不修改库存数字。查询抛 `DataAccessException` 时记「预警不可用」日志并返回，日志只含 SKU、数量、阈值，且不得改变已经成功的扣减返回值。

不改服务接口和 HTTP 返回；不改 Mapper 与库存 SQL；不吞掉扣库存本身的异常。取消释放、退货、后台改库存、商品表 `pms_product.stock/low_stock` 都不在本次改动里。不把预警扩展成短信或邮件。

## 现状与调用链

商品与 SKU 是两套库存。`pms_product`（`document/sql/mall.sql:1085`）只有 `stock`（1109）、`low_stock`（1110），没有锁定库存；模型 `PmsProduct.stock/lowStock` 在 68、71 行。`pms_sku_stock`（1660）才有 `stock`（1665）、`low_stock`（1666）、`lock_stock`（1670）；模型 `PmsSkuStock` 的对应字段在 18、21、33 行。订单实现里没有 `setStock` / `getStock`，不写商品表。

控制器类映射是 `/order`（`OmsPortalOrderController.java:27`）。后台 SKU 更新映射是 `/sku`（`PmsSkuStockController.java:20`），方法为 `POST /update/{pid}`（33 行）。

## 锁定现状的测试

[SDCE500Test](../../../../mall-portal/src/test/java/com/macro/mall/sdc/e5/SDCE500Test.java) 用真实 `paySuccess(9, 1)`，Mock 订单 Mapper 与 `PortalOrderDao`。`updateSkuStock` 返回 3。调用前把 `selectByPrimaryKey(7L)` 打成 stock=10、lockStock=6、lowStock=5（Issue #26 的验收数据，可售 4，已低于阈值）。基线不调用 select，这条打桩不会被读到，也不会产生日志。

- 59 行：返回值是 3（扣减行数）。
- 60 行：确实调用了 `updateSkuStock`。
- 61 行：没有 `updateByPrimaryKeySelective`，支付路径不经 `skuStockMapper` 写库存。
- 63 行：没有 `selectByPrimaryKey`，也就是这条路径不读含 `lowStock` 的 SKU 行。
- 64 行：`OmsPortalOrderServiceImpl` 的日志为空，没有预警。

63、64 行放在 62 行的 `assertAll` 里，实现预警后会一起失败；59–61 行仍应保持。临时 detached worktree 套上 E6-00 的产品补丁后，这两条都失败，记录在 [evidence/injection.txt](evidence/injection.txt)。本测试不断言等于阈值、null、读失败降级或 `generateOrder`。基线上「读失败仍返回 3」也会通过，因为基线根本不查询；红灯将来应来自缺少预警，而不是来自这条返回值断言。

## 落点与被排除的方案

落点是 `OmsPortalOrderServiceImpl` 的私有方法，两个写点之后各调用一次。下单和支付已经在这个类里，Mapper 也已经注入，不必新 Bean、新接口。

排除：

- 在 `updateSkuStock` 的 SQL 里判断阈值。这条语句同时减 `stock` 和 `lock_stock`（53-61 行），可售不变，看不出"刚跌破"；SQL 也不能记日志。把判断写进更新语句，就和"只读、不改库存"冲突。
- 用定时任务扫描 `pms_sku_stock`。现成的 `OrderTimeOutCancelTask`（24 行）做的是取消订单，而且 `@Component` 被注释（14 行）。即便启用，也不是交易完成后立刻告警。
- 改看商品表 `pms_product.low_stock`。商品表没有锁定库存，订单也不更新商品库存，阈值对不上可售。
- 新增公开接口或独立预警 Bean。控制器和支付宝都要改调用，而 Issue 要求服务接口和 HTTP 返回不变。

## 兼容、数据与失败风险

触发顺序：先完成锁定或扣减，再读 SKU；先判空，再做 `<` 比较；读失败只退出预警，不改已经算出的 `count`。

- R1 读失败滚进事务。`paySuccess` 和 `generateOrder` 都有 `@Transactional`（32、26 行）。若 `selectByPrimaryKey` 的异常冒出方法，已成功的扣减会被回滚。捕获范围只能是读操作上的 `DataAccessException`，不能包住 `updateSkuStock` 或 `lockStock`。
- R2 等于和空值。可售等于 `lowStock` 不告警；SKU 缺失或三个数量字段有空值时不告警，也不做减法。
- R3 付款重复告警。扣减 SQL 不改变可售。同一 SKU 若在锁定后已经低于阈值，付款时再读会再记一条。计划接受重复日志，不去重，也不改 SQL。
- R4 旧的空锁定。`lockStock` 第 737 行对 null 的 `lockStock` 会拆箱失败。这是现有语句，本次不修。预警必须自己判空，不能依赖它。
- R5 后台 REPLACE 重置锁定。`PmsSkuStockDao.xml:18` 的列没有 `lock_stock`。REPLACE 先删后插，`lock_stock` 用表默认 0（`mall.sql:1670`）。之后支付或取消再减锁定，锁定会变负，可售被高估，低于阈值也可能不告警。这是现有缺陷，本次不修，预警可能因此失真。
- R6 后台改库存、商品表、取消释放、退货都不告警。不能把「交易后预警」说成这些入口也已覆盖。取消释放由 T10 计划锁定；后台、商品表和退货同样不改，本分支不另写测试。

数据上不增列、不改历史行。兼容上 `paySuccess` 仍返回扣减行数，`generateOrder` 的 Map 不变。
