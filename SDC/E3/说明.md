当前 Java 入口：`src/test/java/com/macro/mall/sdc/e3/OrderIntegrationTest.java`。运行方法见《操作说明.md》。以下“本轮”及覆盖率数字记录迁移前的历史评审；迁移后结果见 `../evidence/java-migration/`。

用户故事：下单者使用的积分和订单赠送的积分必须分别持久化，后写不能覆盖先写。规格在《操作说明.md》。原提交为 `dcaa93b3150352e5044708d7211b5bed0af4509f`。

## 缺陷与修复

调用链：`OmsPortalOrderController.generateOrder` → `OmsPortalOrderServiceImpl.generateOrder` → `OmsOrderMapper.insert`。原实现先把消耗写入 `integration`，再用赠送覆盖该字段，并在插入后才设置 `useIntegration`；因此数据库插入参数缺少消耗值。

当前修复把消耗写入 `useIntegration`，且放在 `orderMapper.insert` 前；赠送继续由 `calcGifIntegration` 写入 `integration`。未使用时保持原有 null，明确使用0时记录0，使用30、赠送12时插入参数分别为30和12。不改生成模型、表结构或服务签名。

根因深挖：旧 Python 程序仅扫描 setter 并自行重放，既不会执行积分合法性判断，也不会调用真正的插入边界；它把4个断言通过数称为覆盖率。这不是 Java 覆盖率。本轮使用真实 `generateOrder`，只替换数据库、Redis、消息发送等外部依赖，在 Mapper 接收到插入参数的当时检查字段，避免测试后读到同一对象后续修改而误通过。

## 证据

- `ExperimentOrderTest.pointsArePersistedSeparatelyBeforeInsert` 分别运行 null、0、30 三例；额外验证无地址、无库存、不可用优惠券不会继续下单。
- `java-evidence/original-order.log`：将原提交的订单实现放入临时目录运行同一测试，0与30两个消耗积分断言失败，另有E6预警断言失败；没有基础设施错误。这是本轮重建的红灯，不冒称过去已经遵循测试先行。
- `java-evidence/current.log`：本轮7项 Java 测试通过，其中 E3 三个参数化积分案例与一个非法订单案例通过。
- `java-evidence/jacoco.xml`：订单服务 `generateOrder` 行覆盖98/107＝91.59%，分支33/40＝82.50%；本次两个积分字段赋值和插入调用均执行。这里不是整个服务、整个模块或 HTTP 控制器的覆盖率。

本轮补充“达标”的数值口径为目标方法行覆盖、分支覆盖均至少80%，并要求 null/0/正数三例在插入边界断言通过。原方案没有给出数字，本轮口径不是历史预注册规则，不以它替代功能验收。
