## ① 修改前的缺陷，以及改了哪里

这次没有改 mall 的业务代码。导读要先看清不能动的边界，再决定以后改哪一层。

缺陷在接口名字和实际行为不一致。`OmsPortalOrderController.java:64-68` 的 `/order/cancelOrder` 名叫“取消单个超时订单”，方法体只调用 `portalOrderService.sendDelayMessageCancelOrder(orderId)`。真正把订单改成关闭状态的是服务里的 `cancelOrder`，调用者是消息接收者 `CancelOrderReceiver.java:22-23`，数据从 TTL 队列到期后进入 `mall.order.cancel`。用户马上取消走的是同一控制器 `:92-96` 的 `/cancelUserOrder`，那里才会直接调用 `cancelOrder`。

下单数据流：控制器 `:43-45` → `OmsPortalOrderServiceImpl.generateOrder` → `:230` 的 `orderMapper.insert`（生成的 `OmsOrderMapper.java:15`）→ `:250` 发出延迟消息。支付数据流：控制器 `:51-52` → `paySuccess` `:258` 起，`:268` 调用 `PortalOrderDao.updateSkuStock`，`:272` 返回更新行数。

课程侧新增的是核对程序，不是业务修改：`SDC/E1/src/main/java/com/macro/mall/sdc/e1/MallFacts.java` 读取七个模块的 `pom.xml` 和这几处源码。`mall-mbg` 下的生成文件没有改。

## ② 原则和取舍

修改前，`/order/cancelOrder` 违背“名字与行为一致”。调用者如果按接口名理解，会以为订单已经取消，实际只是又投递了一次延迟消息。生成代码边界本身是遵守的：`OmsOrderMapper` 留在 `mall-mbg`，手写 SQL 在 `PortalOrderDao`。

这次不把这个接口改掉。E1 的任务是标出边界和调用链；把控制器改成直接取消，会和延迟消息、`/cancelUserOrder` 两条已有路径缠在一起，那是后面 E2 要比较的方案。取舍是：现在只把缺陷钉在行号上，避免在还没写清不可变约束时改交易代码。

依赖方向按开发视图核对。直接边是 admin/portal → mbg 与 security，security → common，并且 mbg 也直接依赖 common。admin 和 portal 的 pom 里没有直接依赖 common，传递依赖不画成直接边。

## ③ 历史验证（迁移前 Python 运行，不是本次 Java 结果）

命令：

```bash
python3 -m unittest experiments/E1/tests/test_e1_mall_facts.py -v
```

结果：3 项通过。

- `test_direct_module_edges` 固定了八条直接依赖，包括方案正文没写的 `mall-mbg → mall-common`，以及 search、demo 不依赖 security。
- `test_cancel_http_only_sends_delay_message` 固定了 `/order/cancelOrder` 的方法体只出现 `sendDelayMessageCancelOrder`，不出现 `portalOrderService.cancelOrder`。
- `test_delay_message_reaches_cancel_order` 固定了发送者走 TTL 队列、接收者监听 `mall.order.cancel` 并调用 `cancelOrder`。

这些测试证明阅读结论和当前源码一致。它们不证明下单或取消在数据库里真的成功，因为没有启动 MySQL 和 RabbitMQ。
