# SDC 学生操作手册：每次完成一个小任务

SDC = software design and conventions。你不用先学会整个商城：**只打开mall，运行本次实验，解释一个设计决定。** 学习边界是[理论章节](课程理论章节.md)、[实验方案](课程实验方案.md)和[考核方案](课程考核方案.md)，不增加课程、评分项或额外平台。

## 1. 第一次只做这三步

**① 拿到一个仓库。** 已有课程机器上的完整仓库就直接打开。需要自己下载时，在准备存放项目的目录执行：

```sh
git clone https://github.com/meng004/mall.git
cd mall
git fetch origin --tags
```

不要加 `--branch sdc-java-migration`。`sdc-java-migration` 只放课程文档，并且含教师参考实现，不是做作业的起点。不需要克隆两个前端或 mall-swarm，也不需要先装 Node、Docker 或模型 CLI。课程机器上若命令前面有 `rtk proxy`，那是教师环境的包装；没安装时用上面的普通命令。第一次下载 Maven 依赖要联网，课前由教师或助教协助；依赖进本地仓库后，实验测试可以离线运行。

**② 用 IDEA 打开 `mall/pom.xml`。** JDK 选 17，Maven Importer 与 Runner 也选 17，重新加载 Maven。打开的是整个 mall，不是某个 E 目录。自备电脑需要 Git、JDK 17、Maven 3.x 和 IDEA；安装问题查[教师环境准备](教师环境准备.md)，不必读完整页后才开始。

**③ 在基线上做一次能通过的构建。** 在 **mall 目录**执行：

```sh
git switch -c e1-<学号> baseline-dcaa93b3
mvn -B -DskipTests -Ddocker.skip=true -pl mall-portal -am package
```

`baseline-dcaa93b3` 与 `origin/sdc-teaching` 是同一提交 `dcaa93b3`。写成 `git switch -c e1-<学号> origin/sdc-teaching` 也可以。E1 没有脚手架，个人分支从这条基线拉出。

要加 `-Ddocker.skip=true`：根 `pom.xml` 第 36 行把 `docker.host` 写成了 `http://192.168.3.101:2375`。`mall-portal/pom.xml` 引用 `io.fabric8` 的 `docker-maven-plugin`，打包阶段会执行 `docker:build`。该插件的 `skip` 对应用户属性 `docker.skip`。不加这个参数，打包会去连接写死的那台 Docker。看到 `BUILD SUCCESS` 就完成首次检查。这还不是 E1 的全部作业。没有 `SDC/E1` 这个模块，也不要找 `MallFactsTest`。

这条构建使用 `-DskipTests`，surefire 的 JUnit 组件可能还没下载，而 `SDC/compare.sh` 默认离线。第一次运行若改前改后都是 `error`，用 `MVN_OFFLINE= SDC/compare.sh E<n>-<学号>` 允许下载依赖。

## 2. 实验分支怎么用

E2 到 E7 每次从该实验的脚手架开个人分支，不要从 `sdc-java-migration` 开：

```sh
git fetch origin
git switch -c e<n>-<学号> origin/exp/E<n>
```

脚手架在基线代码之外还有 `SDC/compare.sh`、`SDC/environment/`、`SDC/E<n>/说明.md` 和 `.github/workflows/sdc-compare.yml`，不含任何示例答案。`exp/E2` 另有公共视图图件 `SDC/E2/diagrams/`（`mall-logical.html`、`mall-cancel.html`、`mall-dependencies.html`、`mall-runtime.html`）。`exp/E7` 另有共用的 LLM 访问层（`mall-portal/src/main/java/com/macro/mall/portal/llm/`，以及 `mall-portal/pom.xml` 中的 `langchain4j-open-ai`）和评测支持类（`mall-portal/src/test/java/com/macro/mall/sdc/e7/` 下的 `EvaluationSupport` 等）。E1 没有 `exp/E1`，用第 1 节的基线分支。

教师示例和候选示例在分支 `exp/e<n>-<NN>`。`NN=00` 是教师演示。E2 是 [`exp/e2-00`](https://github.com/meng004/mall/tree/exp/e2-00)（[Issue #42](https://github.com/meng004/mall/issues/42)，教师演示）与 [`exp/e2-01`](https://github.com/meng004/mall/tree/exp/e2-01)（[Issue #43](https://github.com/meng004/mall/issues/43)，扩展）。E5 的教师演示是 [`exp/e5-00`](https://github.com/meng004/mall/tree/exp/e5-00)（[Issue #44](https://github.com/meng004/mall/issues/44)），候选是 `exp/e5-01` 到 `e5-06`。Issue 按标签查看，例如 <https://github.com/meng004/mall/issues?q=label%3AE3>。看某个示例相对脚手架改了什么：

```sh
git diff origin/exp/E<n>...origin/exp/e<n>-<NN>
```

自己的测试放在被测模块的 `src/test/java/com/macro/mall/sdc/e<n>/`。已经提交的示例并不都在这个包里：一部分后台测试在 `com.macro.mall.sdc`（没有 `e<n>`），`E4-06` 与 `E5-03`、`E5-04`、`E5-05` 在 `com.macro.mall.portal.sdc`。打开具体类时以该分支上的路径为准。

改前／改后对照写在 `SDC/E<n>/outputs/E<n>-<学号>/compare.env`：

```sh
MODULE=mall-portal
TESTS=你的测试类
EXPECT_BASE=fail
```

可选第四行 `HEAD_ONLY_TESTS=只在改后运行的测试类`。依赖新接缝、拷到基线上无法编译的测试放在这里：它们不参与改前判定，改后必须通过。先提交，再运行：

```sh
SDC/compare.sh E<n>-<学号>
```

结论是「符合」才算对照成立。运行前先提交全部改动、保持工作区干净：改前只带已提交的测试文件，改后直接用当前工作区，`compare.txt` 记录的是最后一次提交号。默认离线。改后必须通过。不要手改 `evidence/compare.txt`。第一次运行若改前改后都是 `error`，用 `MVN_OFFLINE= SDC/compare.sh E<n>-<学号>` 允许下载依赖。

`EXPECT_BASE` 按实验目标选择：

| 实验 | 改前预期 | 含义 |
|---|---|---|
| E2 | `pass` 或 `fail` | 行为保持的结构改进用 `pass`；修正错误行为用 `fail`。在说明里写选择理由 |
| E3 | `fail` | 测试必须真正运行并失败。编译错误不能当作红灯 |
| E4 | `pass` | 特征测试改前改后都通过，断言不改 |
| E5 | `pass` | 只锁定现状，不改产品代码 |
| E6 | `fail`；新接口用 `absent` | 新需求在基线上不成立。`absent` 表示功能还不存在，编译失败 |
| E7 | `absent` | 新业务在基线上不存在 |

`origin/exp/e2-00` 上的 `compare.env` 是一份现成写法：`MODULE=mall-portal`，`TESTS=SDCE200Test`，`EXPECT_BASE=pass`，`HEAD_ONLY_TESTS=SDCE200CancellationTest`。

教师演示 E3-00 是 Mock，不连数据库。复演命令见第 5 节。个人作业要自己写测试和修改，不要把教师文件原样交上去。

作业不推送到教师仓库。需要交代码差异时，用自己的 fork，或导出：

```sh
git diff origin/exp/E<n>...HEAD
```

E1 相对基线导出：`git diff baseline-dcaa93b3...HEAD`。

## 3. 一次课只交一份作品

按[本版分实验评分](课程考核方案.md#rubric-e1)：**一页说明 + ≤2分钟本人录屏**，附本次代码差异/必要证据；不用另交规格书、架构报告、AI记录表和日志大全。图和规格可放在同一页中，用链接指向代码或测试。线上预习、课后48小时内交作品、48小时内评3份同学作品照常完成，不改变权重或截止要求。

直接复用这份一页模板：

| 五问 | 填写内容 |
|---|---|
| 原来的问题是什么？ | 本次场景/缺陷/设计疑点，一两句话 |
| 依据是什么？ | 原则或规范 + 关键文件与当前行号 |
| 我做了什么？ | 改动/分析/选定方案；标明参考实现与本人工作 |
| 为什么这样做？ | 遵循的原则 + 一项代价；分析类实验写方案取舍 |
| 怎样证明？ | 本人运行命令与结果，或前后对照；写明未验证部分 |

页尾加两行即可：**AI使用**（工具、使用范围、采纳/驳回或人工修改）；**证据来源**（本人运行/教师演示/已发布参考结果）。录屏建议先说问题，再展示关键代码和运行结果，最后说结论。不能用AI录屏代替本人讲解。

参考实现已经存在，第一次看不懂是正常的；先看下面指定入口，不用通读源码。E1评分看理解与核实，E5看影响判断与可执行计划，两者不要求产品改动；E2须针对具体原则问题完成局部改动或可运行对照；E3/E4/E6要有本人实现与验证，不能只复述教师答案。E7重点是普通／LLM职责分工、业务事实和诚实验收，不要求先造有缺陷的AI初版；课程成绩与业务放行分开。

个人提交须选择不同于教师示例的靶点，见[候选库](教师候选靶点库.md)。逐题源文件、步骤与验证命令见[Cursor产出计划](Cursor候选靶点产出计划.md)；一次只执行所选编号，不执行整库。下文保留的积分、促销、库存等步骤是教师参考演示，不能直接作为个人成果。

## 4. 每次实验的最短路径

下面的积分、促销、库存和商品查询是教师演示。个人从候选库另选一题。测试通过只是运行证据，还要按各节末尾写进一页说明。

### E1：看清模块和调用链

目标：知道系统由什么组成，生成代码在哪里，请求怎样走。

1. 在第 1 节的基线分支上对照根 POM 的模块依赖。下单、支付、超时取消的入口是：
   - `mall-portal/src/main/java/com/macro/mall/portal/controller/OmsPortalOrderController.java`
   - `mall-portal/src/main/java/com/macro/mall/portal/service/impl/OmsPortalOrderServiceImpl.java`
   - `mall-portal/src/main/java/com/macro/mall/portal/component/CancelOrderSender.java`
   - `mall-portal/src/main/java/com/macro/mall/portal/component/CancelOrderReceiver.java`

   沿控制器到服务阅读下单和支付，再看 `CancelOrderSender` 与 `CancelOrderReceiver`。延迟取消不是下单当时就取消。
2. 公共 4+1 视图在脚手架 [exp/E2 的说明](https://github.com/meng004/mall/blob/exp/E2/SDC/E2/说明.md)「公共 4+1 视图」。图在该分支 `SDC/E2/diagrams/`：`mall-logical.html`、`mall-cancel.html`、`mall-dependencies.html`、`mall-runtime.html`。E1 不运行 `compare.sh`。
3. 只读商品查询是 E1 的评分项，占「验证过」中的 20 分（与本人完成的构建、导读写在同一项）。在教师准备好的课程机器上做，命令见第 5 节。

**放进一页说明**：模块图和 `mall-mbg` 生成代码边界、一条调用链、一个设计疑点和一次理解纠正。验收：能说明延迟取消不是立即取消；测试与商品查询有本人操作证据。无需启动前端。

### E2：用原则和证据解释一次设计改进

目标：定位分层中的具体设计原则问题，用 SOLID、Clean Code 等原则解释，证明局部改进。

1. 从候选库选一个非教师示例，给出文件与行号、调用者或数据流。说明具体失败或变更场景，不把方法长或 Service 调用 Mapper 自动判错。教师演示是 [`exp/e2-00`](https://github.com/meng004/mall/tree/exp/e2-00)（[Issue #42](https://github.com/meng004/mall/issues/42)），扩展是 [`exp/e2-01`](https://github.com/meng004/mall/tree/exp/e2-01)（[Issue #43](https://github.com/meng004/mall/issues/43)）。旧 E2-01～07（#5–#9、#40）已关闭，不作选题。
2. 用第 4 节 E1 指向的公共 4+1 视图解释职责与依赖；比较两种最小方案在可测试性、可替换性和成本上的区别，选择一个局部落地点。
3. 完成该局部改动或可运行对照。测试放在被测模块，提交后运行 `SDC/compare.sh E2-<学号>`。`EXPECT_BASE` 用 `pass` 或 `fail`，见第 2 节。说明见 [exp/E2](https://github.com/meng004/mall/blob/exp/E2/SDC/E2/说明.md)。

**放进一页说明**：改前问题与改动位置、原则和取舍、测试／前后结果。只提交两张设想图或方案文字，不算已验证改进；不要求实施整套重构、部署 swarm 或增加报告。

### E3：规格与失败测试（以下为积分教师示例）

目标：用规格和失败测试约束 AI 修改。

1. 教师演示是 [`exp/e3-00`](https://github.com/meng004/mall/tree/exp/e3-00)，[Issue #10](https://github.com/meng004/mall/issues/10)。先写三种输入的期望：使用积分 null、0、30；使用 30 且赠送 12 时，订单插入参数分别为 `useIntegration=30`、`integration=12`。不改生成代码、表结构和公开接口。
2. 测试类是 `SDCE300Test`，路径 `mall-portal/src/test/java/com/macro/mall/sdc/e3/SDCE300Test.java`。`compare.env` 为 `MODULE=mall-portal`、`TESTS=SDCE300Test`、`EXPECT_BASE=fail`。在 `SDCE300Test` 里 Debug 到真实 `generateOrder` 与 Mapper 插入处；先观察失败，再只修复积分字段覆盖。说明 AI 建议中采纳/驳回什么。复演命令见第 5 节。
3. 其他示例是 `exp/e3-01`、`e3-02`、`e3-03`、`e3-04`、`e3-06`、`e3-07`（没有 `e3-05`），见 [Issue 标签 E3](https://github.com/meng004/mall/issues?q=label%3AE3)。`SDCE303Test`、`SDCE304Test`（还有 `SDCE304TransactionTest`）、`SDCE306Test` 在 `mall-admin` 的 `com.macro.mall.sdc`。个人从 `origin/exp/E3` 开 `e3-<学号>`。E3 要求本人实际修改的目标方法行、分支覆盖率均不低于 80%（教师演示的目标方法是 `generateOrder`）。在修复之后的工作区执行 `exp/e3-00` 证据文件 `SDC/E3/outputs/E3-00/evidence/coverage.txt` 中的命令：

```sh
mvn -B -pl mall-portal -am -DskipTests=false -Dtest=SDCE300Test -Dsurefire.failIfNoSpecifiedTests=false org.jacoco:jacoco-maven-plugin:0.8.13:prepare-agent test org.jacoco:jacoco-maven-plugin:0.8.13:report
```

命令里的 `-Dtest=SDCE300Test` 要换成自己的测试类，报告里看自己实际修改的方法。上面这条是教师演示，看的是 `generateOrder`。文档核对时（2026-10-07）在 `exp/e3-00` 上离线重跑该命令，`BUILD SUCCESS`；`generateOrder` 行覆盖 95/104（91.3%），分支 31/38（81.6%）。说明见 [exp/E3](https://github.com/meng004/mall/blob/exp/E3/SDC/E3/说明.md)。

**放进一页说明**：规格小表、失败断言、修复理由和当前结果。验收：错的是业务断言而非环境；3种积分输入均正确，沿用E3目标方法覆盖率要求。教师日志不能冒充自己的运行。

### E4：保住行为，再改结构（以下为优惠券范围策略教师示例）

目标：理解优惠券适用范围策略重构的收益和成本。

1. 教师演示是 [`exp/e4-00`](https://github.com/meng004/mall/tree/exp/e4-00)，[Issue #20](https://github.com/meng004/mall/issues/20)，优惠券适用范围的策略重构。测试类 `SDCE400Test`，路径 `mall-portal/src/test/java/com/macro/mall/sdc/e4/SDCE400Test.java`。`EXPECT_BASE=pass`。重跑同一组测试，核对可用与不可用券的划分保持一致。
2. 个人从 `origin/exp/E4` 开 `e4-<学号>`，按所选靶点先写特征测试再重构（教师演示是把优惠券范围分支收成策略）。解释新增一种范围时需要改哪些地方。不改变公开接口。没有 `e4-05`。说明见 [exp/E4](https://github.com/meng004/mall/blob/exp/E4/SDC/E4/说明.md)。

**放进一页说明**：坏味道、模式四要素、前后结果和代价。验收：既说得清为什么重构，也证明行为没变；不重构整个订单系统。

### E5：先写变更计划

目标：知道低库存预警影响哪些代码。

教师演示 E5-00（[`exp/e5-00`](https://github.com/meng004/mall/tree/exp/e5-00)，[Issue #44](https://github.com/meng004/mall/issues/44)）以“库存低于阈值时给出预警”为需求，与 E6-07（[`exp/e6-07`](https://github.com/meng004/mall/tree/exp/e6-07)，[Issue #26](https://github.com/meng004/mall/issues/26)）同一需求。

1. 候选是 `exp/e5-01` 到 `exp/e5-06`，见 [Issue 标签 E5](https://github.com/meng004/mall/issues?q=label%3AE5)。测试类是 `SDCE501Test` 到 `SDCE506Test`，`EXPECT_BASE=pass`。区分商品库存与 SKU 的 `stock` / `lockStock` / `lowStock`：基线 `PmsProduct` 有 `stock`、`lowStock`；`PmsSkuStock` 有 `stock`、`lockStock`、`lowStock`。只加锁定现状的测试和分析，不改产品代码，也不在这次实现预警。
2. `E5-01`、`E5-02`、`E5-06` 的测试在 `mall-admin` 的 `com.macro.mall.sdc`；`E5-03`、`E5-04`、`E5-05` 在 `mall-portal` 的 `com.macro.mall.portal.sdc`。提交后运行 `SDC/compare.sh E5-<学号>`。说明见 [exp/E5](https://github.com/meng004/mall/blob/exp/E5/SDC/E5/说明.md)。
3. 对照调用链，写下单锁定、支付扣减、取消释放、退货和后台编辑里与本题相关的点；写准备改的文件、不能改的边界、回归范围，并排除一个不合适的方案。

**放进一页说明**：影响关系与变更清单、回归依据、一个风险及验证办法。验收：能说明为什么检查这些调用链；不要求此时实现预警。

### E6：规格驱动变更（以下为会员价教师示例）

目标：把选定需求改成可验证的小变更。

1. 教师演示是 [`exp/e6-00`](https://github.com/meng004/mall/tree/exp/e6-00)，[Issue #14](https://github.com/meng004/mall/issues/14)。先用特征测试固定促销计算、重构出策略接缝，再按规格落地购物车会员价。测试类名见 Issue #14。选现有两套编码规范的一处分歧，写一句本次取舍；无需另写规范报告。

## 6. 卡住时先做什么

| 现象 | 最短处理 |
|---|---|
| 编译版本错误 | 看 `mvn -version` 是否Java17，再看IDEA Runner；不要重装整个工程 |
| 找不到模块或类 | 确认在 mall 根目录，测试类在被测模块的 `src/test/java`；用 `-pl <模块> -am -DskipTests=false -Dtest=<测试类> test` |
| 下载失败 | 请助教处理网络/缓存，或换已准备好的课程机器；不是代码缺陷证据 |
| 数据库/模型连接失败 | 先做离线测试和分析，记录未完成部分，再补实际运行 |
| 测试失败 | 找第一个失败断言，对照期望与实际；保留失败，不删测试凑绿灯 |
| 看不懂业务类 | 从本次测试的输入、动作、断言反向定位，不通读整个商城 |

评分仍看“讲清楚、有依据、验证过”，不看安装了多少工具、报告多长或新增了多少代码。先完成本次小任务，再改进解释；不额外设置拓展作业、排行榜或工具使用奖励。
