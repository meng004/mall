# SDC 学生操作手册：每次完成一个小任务

SDC = software design and conventions。你不用先学会整个商城：**只打开mall，运行本次实验，解释一个设计决定。** 学习边界是[理论章节](课程理论章节.md)、[实验方案](课程实验方案.md)和[考核方案](课程考核方案.md)，不增加课程、评分项或额外平台。

## 1. 第一次只做这三步

**① 拿到一个仓库。** 已有课程机器/教师提供的完整仓库就直接打开；需要自己下载时，在准备存项目的文件夹打开终端：

```sh
rtk proxy git clone --branch sdc-java-migration https://github.com/meng004/mall.git
```

不需要克隆两个前端或mall-swarm，不需要先装Node、Docker或模型CLI。命令中的 `rtk proxy` 是教师仓库约定；普通Git/Maven命令未安装RTK时可去掉这个前缀。第一次下载依赖要联网，课前由教师/助教协助准备；缓存齐备后实验测试可离线运行。

**② 用IDEA打开 `mall/pom.xml`。** JDK选17，Maven Importer与Runner也选17，重新加载Maven。不是只打开某个E目录。自备电脑只需Git、JDK17、Maven 3.x和IDEA；具体安装遇到问题查[教师环境准备](教师环境准备.md)，不必读完整页后才开始。

**③ 先跑一个小测试。** 在 **mall目录** 打开终端，执行：

```sh
rtk proxy mvn -pl SDC/E1 -am test
```

看到 `BUILD SUCCESS`、E1的3项测试通过，就完成了首次环境检查。先体验成功，再读代码；这还不是E1全部作业。若没有运行测试或全部Skipped，去掉命令里的 `-DskipTests=true`。IDEA里也可打开 `SDC/E1/src/test/java` 的 `MallFactsTest`，点击类旁运行按钮。

以后每次只把 `E1` 改成对应的 `E2`…`E7`。`-pl`表示选实验，`-am`表示同时构建它需要的模块。**不用每次完整打包、安装四个仓库或重装中间件。**

## 2. 一次课只交一份作品

按[本版分实验评分](课程考核方案.md#rubric-e1)：**一页说明 + ≤2分钟本人录屏**，附本次代码差异/必要证据；不用另交规格书、架构报告、AI记录表和日志大全。图和规格可放在同一页中，用链接指向代码或测试。线上预习、课后48小时内交作品、48小时内评3份同学作品照常完成，不改变权重或截止要求。

直接复用这份一页模板：

| 五问 | 填写内容 |
|---|---|
| 原来的问题是什么？ | 本次场景/缺陷/设计疑点，一两句话 |
| 依据是什么？ | 原则或规范 + 关键文件与当前行号 |
| 我做了什么？ | 改动/分析/选定方案；标明参考实现与本人工作 |
| 为什么这样做？ | 遵循的原则 + 一项代价；分析类实验写方案取舍 |
| 怎样证明？ | 本人运行命令与结果，或前后对照；写明未验证部分 |

页尾加两行即可：**AI使用**（工具、使用范围、采纳/驳回或人工修改）；**证据来源**（本人运行/教师演示/已发布参考结果）。录屏建议先说问题，再展示关键代码和运行结果，最后说结论。不能用AI录屏代替本人讲解。

参考实现已经存在，第一次看不懂是正常的；先看下面指定入口，不用通读源码。E1评分看理解与核实，E5看影响判断与可执行计划，两者不要求产品改动；E2须针对具体原则问题完成局部改动或可运行对照；E3/E4/E6要有本人实现与验证，不能只复述教师答案。E7重点是普通／LLM职责分工、业务事实和诚实验收，不要求先造有缺陷的AI初版；课程成绩与业务放行分开。

个人提交须选择不同于教师示例的靶点，见[候选库](教师候选靶点库.md)。逐题源文件、步骤与验证命令见[Cursor产出计划](Cursor候选靶点产出计划.md)；一次只执行所选编号，不执行整库。下文保留的积分、促销、库存等步骤是教师参考演示，不能直接作为个人成果。

## 3. 每次实验的最短路径

所有测试类都在 `SDC/Ex/src/test/java`，下列main入口在相应模块 `src/main/java`。测试通过仅是运行证据，还要按最后一列说明设计依据。

### E1：看清模块和调用链

目标：知道系统由什么组成，生成代码在哪里，请求怎样走。

1. 运行 `MallFactsTest`（3项），再运行 `MallFacts.main`，对照根POM的模块依赖。
2. 沿 `OmsPortalOrderController → OmsPortalOrderServiceImpl` 阅读下单、支付，再看 `CancelOrderSender/Receiver` 的超时取消。复用 `E1/diagrams` 图补标关键关系，不必重新美化。
3. 在教师准备好的课程机器上执行一次真实商品查询（命令见下节），对照响应和服务入口。

**放进一页说明**：模块图和 `mall-mbg` 生成代码边界、一条调用链、一个设计疑点和一次理解纠正。验收：能说明延迟取消不是立即取消；测试与商品查询有本人操作证据。无需启动前端。

### E2：用原则和证据解释一次设计改进

目标：定位分层中的具体设计原则问题，用 SOLID、Clean Code 等原则解释，证明局部改进。

1. 从候选库选一个非教师示例，给出文件:行号、调用者或数据流。说明具体失败／变更场景，不把方法长或 Service 调用 Mapper 自动判错。
2. 用相关 4+1 视图解释职责与依赖；比较两种最小方案在可测试性、可替换性和成本上的区别，选择一个局部落地点。
3. 完成该局部改动或可运行对照，运行测试或做真实前后比较，证明行为保留和所称改善。`LayerRules` 是教师定位示例，旧测试通过不能代替本题证据。

**放进一页说明**：改前问题与改动位置、原则和取舍、测试／前后结果。只提交两张设想图或方案文字，不算已验证改进；不要求实施整套重构、部署 swarm 或增加报告。

### E3：规格与失败测试（以下为积分教师示例）

目标：用规格和失败测试约束AI修改。

1. 先写三种输入的期望：使用积分null、0、30；使用30且赠送12时，订单插入参数分别为 `useIntegration=30`、`integration=12`。不改生成代码、表结构和公开接口。
2. 打开 `OrderIntegrationTest`，Debug到真实 `generateOrder` 与Mapper插入处；先观察失败，再只修复积分字段覆盖。个人练习的起点见第4节。
3. 重跑同组测试（4项）；保留前后差异，说明AI建议中采纳/驳回什么。按现有E3要求核对 `generateOrder` 方法行/分支覆盖率，工具使用由教师课前准备，不让全班重复安装。

**放进一页说明**：规格小表、失败断言、修复理由和当前结果。验收：错的是业务断言而非环境；3种积分输入均正确，沿用E3目标方法覆盖率要求。教师日志不能冒充自己的运行。

### E4：保住行为，再改结构（以下为促销教师示例）

目标：理解促销策略重构的收益和成本。

1. 在个人练习起点运行 `PromotionTest`，先固定7组行为（金额、文案、库存、积分和成长值）。原版E4本来就应通过。
2. 只将促销分支组织为策略，不改变公开接口；对照参考实现，解释新增一种促销时需要改哪些地方。
3. 重跑相同测试（1个JUnit方法内7组案例），核对满减3.3000等结果保持一致。

**放进一页说明**：坏味道、模式四要素、前后结果和代价。验收：既说得清为什么重构，也证明行为没变；不重构整个订单系统。

### E5：先写变更计划（以下为库存教师示例）

目标：知道低库存预警影响哪些代码。

1. 运行 `StockImpactTest`（E5自身3项，含E1共6项）和 `StockImpact.main`，区分商品库存与SKU的 `stock/lockStock/lowStock`。
2. 对照现有调用链，找下单锁定、支付扣减、取消释放、退货和后台编辑的相关点。
3. 写准备改的文件、不能改的边界、回归范围，并排除一个不合适方案。

**放进一页说明**：影响关系与变更清单、回归依据、一个风险及验证办法。验收：能说明为什么检查这些调用链；不要求此时实现预警。

### E6：规格驱动变更（以下为预警教师示例）

目标：把E5的模糊需求改成可验证的小变更。

1. 写清规格：可售=`stock-lockStock`；严格低于SKU的 `lowStock` 才告警，等于/阈值null不告警；读取告警数据失败不能改变已成功交易的返回值。
2. 在个人起点先运行 `StockWarningTest` 观察缺失告警，再在实际服务增加预警；不改库存SQL、公开接口和生成代码。
3. 重跑测试（2项），核对日志与返回值。选现有两套编码规范的一处分歧，写一句本次取舍；无需另写规范报告。

**放进一页说明**：用户故事与验收/非功能要求、代码差异、测试、接口兼容与规范取舍。验收：预警没有额外扣库存或拒绝成功交易；不把单元测试称为真实事务/并发验证。

### E7：改进一个有明确边界的 AI 业务

目标：按[候选库的六项业务](教师候选靶点库.md#e7-business)选一项，提供普通与 LLM 实现，验证 AI 接入的设计改进。

1. 教师的 `ProductQueryService`、`LlmClient` 和查询测试用于理解接入方式；个人业务从订单问答、规格比较、退货材料、评论分类、属性提取、退货原因分析中选一项。
2. 提供普通与LLM两种实现，模型访问复用LlmClient；说明理解、事实／计算、身份及错误处理由谁负责，给出实际文件:行号。没有AI不算原系统违规，不要求不合格初版。
3. 用教师为本题准备的20正常＋8对抗＋4分布外题比较普通／LLM，记录结构化结果、依据、错误和耗时，另验证模型不可用及降级。按预定阈值作放行／降级／驳回；不能删题凑分，不要求每人另编32题或购买账号。

**放进一页说明**：业务数据流、职责与原则、实际实现、普通与LLM的取舍、独立评测和失败处理证据。模型不可用时可先完成离线检查并说明在线未完成；不能用教师已有查询成绩代替所选业务验收。

## 4. 需要时才看：查询与修改起点

### E1真实查询 / E7演示

教师按[环境准备](教师环境准备.md)启动既有Compose和portal后，学生在该课程机器终端执行：

```sh
rtk proxy curl --noproxy '*' 'http://127.0.0.1:18085/product/search?keyword=HUAWEI%20P20&pageNum=1&pageSize=5'
```

`code=200`且返回商品26为样例库预期。未运行服务时出现连接失败是环境问题，先继续代码阅读与测试，稍后在就绪机器补做查询，不把失败写成通过。自备电脑需本地运行时只按教师页的Compose步骤做，不复制老师电脑路径，不导入/清空已有数据库。

E7用IDEA运行 `QueryDemo.main`，工作目录mall，环境变量 `SPRING_CONFIG_ADDITIONAL_LOCATION=file:./SDC/environment/application-sdc.yml`；参数先填 `existing 小米`，再填 `llm "名称包含小米且价格小于3000"`。模型变量由教师在本人授权的课程机器安全配置，不把教师token发给学生。普通文本查询只按名称关键词，不会理解价格。完整接口与评测器操作见[E7说明](E7/操作说明.md)。

### E3/E4/E6教师示例复演起点

以下历史恢复只用于复演教师示例，不是替代候选的统一起点，不能恢复订单文件来修复后台候选。候选按库中对应模块写自己的测试。参考分支已经包含答案。为练习“先失败后修复”，在**干净的mall工作区**先建本次个人分支，保留SDC测试，只把本次业务文件恢复为历史原版。先用 `git status --short` 检查；有未提交作业就先保存到自己的提交，不能覆盖。

```sh
rtk proxy git status --short
rtk proxy git switch -c practice-e3
rtk proxy git restore --source=dcaa93b3150352e5044708d7211b5bed0af4509f -- mall-portal/src/main/java/com/macro/mall/portal/service/impl/OmsPortalOrderServiceImpl.java
rtk proxy mvn -pl SDC/E3 -am test
```

预期E3出现两个积分业务断言失败，编译错误不算成功复现。开始修复时保留这份测试；对照参考分支只看需要理解的差异，不整份抄回当作本人实现。

E4从教学分支新建 `practice-e4`，只恢复 `OmsPromotionServiceImpl.java`，运行E4测试；E6新建 `practice-e6`，只恢复上例订单服务文件，运行E6测试。IDEA Git分支菜单可切换；每次先保存当前改动再切换，不在同一分支叠加原版恢复。恢复订单服务也移除了参考版另一实验的改动，所以练习期只运行所选实验；全套32项通过适用于教师参考分支，不能要求未做E6的E3练习分支全绿。完成后提交本人差异，不推送教师仓库。

E3只按[E3详细页的“个人E3分支的覆盖率”](E3/操作说明.md)执行两条命令，不会运行E6。JavaEvidence综合对照限教师完整参考分支使用；个人E4/E6只运行本实验测试。它们是同一作业的验证方法，不是另一份作业。

## 5. 卡住时先做什么

| 现象 | 最短处理 |
|---|---|
| 编译版本错误 | 看 `mvn -version` 是否Java17，再看IDEA Runner；不要重装整个工程 |
| 找不到模块或类 | 打开mall根POM，在mall目录用 `-pl SDC/Ex -am test` |
| 下载失败 | 请助教处理网络/缓存，或换已准备好的课程机器；不是代码缺陷证据 |
| 数据库/模型连接失败 | 先做离线测试和分析，记录未完成部分，再补实际运行 |
| 测试失败 | 找第一个失败断言，对照期望与实际；保留失败，不删测试凑绿灯 |
| 看不懂业务类 | 从本次测试的输入、动作、断言反向定位，不通读整个商城 |

评分仍看“讲清楚、有依据、验证过”，不看安装了多少工具、报告多长或新增了多少代码。先完成本次小任务，再改进解释；不额外设置拓展作业、排行榜或工具使用奖励。
