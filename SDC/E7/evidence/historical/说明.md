# E7 实现与验收证据

## 缺陷及根因

旧实现没有调用模型或运行中的mall，只读SQL种子副本；识别问句时按商品词命中，执行时却拿整句匹配商品名，因此“请查询HUAWEI P20”被标ok但返回空。库存提案按任一词扩大到两个商品，确认逻辑硬编码库存0，因此“改成5”被执行成两个商品清零。所谓盲评是写在测试里的4题，泄漏参数硬编码为0，不能据此放行。

本轮修复以模型白名单意图为共同语义：`cursor_model.CursorModel` 调用用户指定的 Cursor `grok-4.7-high-fast`；`nl_query.Session.ask` 校验动作、字段和数值，`PortalCatalog.search` 调用既有 `GET /product/search`，商品过滤仍由mall服务落实，再应用价格/库存AND条件。模型不能提供SQL、URL或替换数据源。旧的SQL种子解析和按结果条数制造置信度已移除。

真实数据流：终端问句 → Cursor Grok结构化意图 → Python硬校验 → mall `PmsPortalProductController.search` → `PmsPortalProductServiceImpl.search` → 生成Mapper参数化查询 → MySQL → 仅展示公开商品字段与id/接口来源。

用户已确认关键操作限定为库存草稿：唯一目标与准确数值先显示再确认，结果标 `draft_only`，只写会话草稿表；撤销恢复上一草稿，任何新请求清理旧待确认项。不新建库存写入接口、不修改订单、数据库库存或mall.sql。草稿不是已落库库存，不能声称真实库存写入或撤销已验收。

## 验证

新11项Python测试通过，覆盖组合查询、小数与严格边界、准确草稿值、歧义目标、模型臆造写入、注入清理待确认项、非法结构、故障降级及模型适配器失败；使用固定模型输出的单元测试仅验证接入代码，不计入模型准确率。

真实烟测：`请查询HUAWEI P20` 经Grok及运行中的portal返回 `source=[26]`、价格3788.00、商品库存1000，来源 `http://127.0.0.1:18085/product/search`；置信度0.96标为模型自报未校准，不参与授权。该单题不能支持总体准确率。

留出验收按《操作说明.md》的20正常/8对抗/4分布外/2草稿及95%准确率、零泄漏标准运行；原始问题、独立期望、逐题模型意图与结果保存于 `evaluation/`。本轮 `evaluation/holdout-1-result.json` 记录34/34通过：正常20/20、对抗8/8、分布外4/4、草稿2/2，泄漏0；在用户确认的查询/草稿范围内放行。最大单题23.197秒，不外推吞吐或生产延迟。旧“4/4放行”结论作废。独立代码复审另发现案例种类缺项仍能放行，已在原判定处落实20/8/4/2最低数量，回归测试通过；这一轮本身具备全部案例，因此结论不变。

## 取舍与适用范围

使用已有HTTP商品接口，避免新增控制器和数据库写入面；代价是价格/商品库存条件在取回公开商品后过滤，超过2000条要求缩小查询，后端及模型失败走手工关键词入口。本地Cursor逐次进程调用适合课程验证，不声称高并发生产性能。

输入过滤用于拒绝已知风险词，但核心边界是固定只读接口、公开字段投影和结构校验；模型置信度仅展示。未支持的比较运算应拒绝，不能悄悄丢掉条件。运行环境权限、模型变更与不同商品数据都会影响复现结果，必须保留报告版本和实际运行时间。
